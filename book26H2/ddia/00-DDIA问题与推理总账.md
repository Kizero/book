# DDIA 问题与推理总账

> 这不是章节摘要，也不是完整对话存档。它只保存能够帮助我们重新推导结论的路标。

## 使用规则

1. 每个小节先由读者阅读原文并完成“原文阅读工作纸”，之后才进入对话；AI 不提前代写原文理解。
2. 只在一个小节、一个机制群或一章形成闭环后更新，不随每轮对话追加。
3. 记录“为什么”：问题、约束、保证、机制、失败方式与代价；不复制大段原文。
4. 一个案例必须同时写明“它说明什么”和“它不能说明什么”，避免把企业故事当作普遍规律。
5. 认知卡只保留会改变以后判断或行动的一点；允许遗漏，后续遇到新证据再修订。
6. 没有改变推理、不能迁移使用的材料，不进入总账。

## 固定学习闭环

```text
带着一个问题阅读原文
→ 合上页面，凭记忆写工作纸
→ 回看原文，区分作者原意与自己的推断
→ 苏格拉底对话：反例、故障、边界与真实案例
→ 回到原文，修正但不覆盖最初判断
→ 节点形成后，才把稳定成果写入总账
```

原文工作纸是过程材料，允许粗糙和犯错；问题与推理总账是节点成果，保持精简。两者不能互相替代。

案例来源标签：

- **事故复盘**：真实故障及恢复证据。
- **企业实践**：企业公开的架构与经营经验，结论受其具体条件约束。
- **官方文档**：产品当前公开能力与责任边界。
- **书籍 / 论文**：用于补充历史、组织和机制解释；需要区分事实、作者观点和时代背景。

## 节点一：同一份数据，为什么会走向不同系统？

### 牵引问题

一个单节点 PostgreSQL 容量尚有余量，但分析查询每天会让在线请求大量超时。应该局部优化，还是增加数据系统并进行负载隔离？

### 推理链

```text
数据库进程仍然存活
→ 但请求延迟超过客户端超时
→ 性能问题转化为用户可见的不可用

分析任务长期占用连接
→ OLTP 请求等待连接
→ 客户端超时并重试
→ 排队进一步恶化

扩大同一个连接池
→ 没有改变共享资源与准入规则
→ 分析任务仍可能耗尽连接，甚至增加数据库并发压力

拆成两个连接池并设置配额
→ 隔离连接准入
→ 但仍共享 CPU、I/O、内存、缓存和锁

把分析负载转移到仓库或派生存储
→ 获得更彻底的负载隔离和针对性数据布局
→ 同时引入复制延迟、同步失败、真相来源与重建问题
```

### 形成的判断

- OLTP 与 OLAP 首先描述访问模式和工作负载，而不是“业务内部 / 外部”、读 / 写或价值高低。
- 判断负载要看访问行列数、随机访问或连续扫描、点查点写或聚合、并发量、延迟要求和数据新鲜度。
- 复杂度不是越少越好；当负载互相伤害时，隔离可能是必须购买的复杂度。
- 隔离也不是免费的：把压力转移到另一系统，会换来派生数据的延迟、失败和一致性问题。

### 从派生数据继续推出的问题

付款风控若直接扫描 30 天流水，结果最新但难以满足在线延迟；若预计算特征，读取只需数毫秒，却可能读取到陈旧或静默错误的结果。

```text
预计算风险特征
→ 在线链路更快、更稳定
→ 特征可能陈旧
→ 并发请求可能同时突破风险边界
→ 必须增加同步的在线业务约束
```

此时要区分：

- **高可用**是非功能目标；
- **业务不变量**是无论并发与故障怎样发生都不能被破坏的业务事实；
- **Trace ID**标识一次执行尝试；
- **Operation ID（OID）**标识跨重试不变的业务意图。

操作幂等与业务名额是两个生命周期：

```text
操作记录：较长期保留
(userId, oid) → status, orderId, requestFingerprint

用户名额：订单在途期间存在
userId → (oid, orderId)

订单履约结束
→ 释放用户名额
→ 仍保留 (userId, oid) → orderId
→ 同一 OID 重试只能得到原订单，新 OID 才能创建新订单
```

由此得到一个可迁移原则：

> 释放业务资源，不等于删除操作结果；资源生命周期与幂等生命周期不同。

### 认知变化

原来主要按照业务用途和使用者区分 OLTP 与 OLAP；现在首先根据访问模式、系统负载、延迟和新鲜度要求判断。同一份数据可能需要不同系统，不只是因为使用目的不同，更因为不同目的产生了互相冲突的访问模式。

## 节点二：云托管与自建，真正改变了什么？

### 牵引问题

核心业务是否因为“重要、机密、需要掌控”，就一定应该自建？云账单与机器采购成本能否直接比较？

### 推理链

```text
核心业务很重要
↛ 必然自建

自建拥有更多操作权
↛ 自动获得更高可靠性

云厂商管理部分基础设施
↛ 云厂商负责业务正确性

机器采购费用低于云账单
↛ 自建全生命周期成本更低
```

云托管与自建首先是在重新分配责任：

- 云托管可接管部分硬件、操作系统、数据库进程、补丁、备份与故障切换机制；
- 客户仍需负责产品选型与配置、数据模型、SQL、连接池、容量、访问控制、业务止损、恢复验收和端到端正确性；
- 自建增加了直接操作和定制能力，也把持续值守、故障恢复和人员连续性责任收回团队。

决策时必须在相同服务目标下比较：

```text
业务负载与增长方式
+ SLO / RTO / RPO
+ 安全、合规与数据驻留
+ 定制需求与退出能力
+ 经压测和演练验证的团队能力
+ 人力、值守、冗余容量、迁移及机会成本
= 可比较的全生命周期方案
```

### 认知卡

原来认为，只要核心业务选择自建，最终就会获得更低的成本、更强的控制力和更灵活的功能迭代。

这个判断主要计算了云服务费用、二次开发难度和功能建设成本，却遗漏了让系统长期高可用运行所需的值守、监控、容量冗余、故障演练、备份恢复、人员培养及机会成本。

现在认为，“核心业务”只是业务重要性标签，不能直接推出“必须自建”。应当在同等可用性、性能、安全、RTO、RPO和可维护性条件下，比较双方承担的责任、实际能力和全生命周期成本。

以后做类似决策，先明确可用性目标、数据体量、峰值吞吐、并发、恢复要求、定制需求和安全边界，再要求候选方案拿出压测、演练、恢复和总成本证据，而不从“云”或“自建”的标签直接得出结论。

### 真实案例锚点

#### GitLab 2017 数据库事故｜事故复盘

- **事实**：GitLab.com 数据库事故导致服务中断约 18 小时，并丢失约 6 小时内的一部分数据库变更。公开复盘显示，备份任务曾静默失败，恢复流程没有定期验证，也缺少明确负责人。
- **说明**：配置了备份，不等于备份成功、能够恢复、能在 RTO 内恢复，或恢复后的业务数据正确。
- **不能说明**：不能由一次事故推出所有自建系统都不可靠；它揭示的是恢复能力必须通过持续验证建立。
- **来源**：[GitLab 官方事故复盘](https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/)

#### 37signals 退出部分云服务｜企业实践

- **事实**：按 37signals 自己的公开复盘，其部分工作负载迁出 AWS 后，云账单年化基线从约 320 万美元下降到约 130 万美元；约 70 万美元硬件投入在迁移期间收回，并预计五年节省超过 1000 万美元。
- **条件**：负载相对稳定、团队经验成熟，而且能够复用已有机房机架与电力条件。
- **说明**：在规模、负载、团队和既有设施满足特定条件时，自建确实可能更经济。
- **不能说明**：这是企业自己的成本口径，不能推出任何公司自建都会更便宜。
- **来源**：[37signals 的公开复盘](https://world.hey.com/dhh/our-cloud-exit-savings-will-now-top-ten-million-over-five-years-c7d9b5bd)

#### Amazon RDS 责任边界｜官方文档

- **事实**：RDS 接管部分硬件、操作系统、数据库软件维护、备份与高可用机制；应用优化、数据模型、查询调优和具体工作负载仍由客户负责。
- **说明**：托管服务改变责任边界，而不是外包整个系统的正确性。
- **不能说明**：产品列出一种能力，不代表客户购买的具体规格、拓扑和配置已经满足自己的业务 SLO。
- **来源**：[Amazon RDS 文档](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Welcome.html)

## 当前总问题链

```text
不同业务目的
→ 产生不同访问模式
→ 不同负载争用资源
→ 需要配额隔离或派生系统
→ 派生系统带来延迟与同步失败
→ 陈旧数据可能破坏业务不变量
→ 需要在线约束、幂等与恢复机制
→ 云与自建决定由谁运营这些机制
→ 但业务正确性与验收责任始终不能外包
```
