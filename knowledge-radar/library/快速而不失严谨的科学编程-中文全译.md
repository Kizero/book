## 引言

编程教材或课程都会告诉你，应当编写结构良好、文档完备、充分测试的程序，以保证正确性并便于维护。但面对时间压力，又急于获得科学结果时，你可能会发现自己采用了快速而粗糙的编码方式，达不到这种理想。事实上，快速编码可以很好地应对计算研究中不确定、探索性的特点。写得越快，你可能检验并发表的科学想法就越多。不过，如果快速意味着草率，结果可能就是程序错误、错误结论和论文撤稿［1］。此外，代码如果随着时间越来越复杂、凌乱，就很难适应新任务，甚至阻碍研究进展。因此，高效的科学编程需要不断平衡现在和未来的需求：可以快速、不精雕细琢，但必须足够严谨。

本指南关注软件开发速度，提出十条简单规则，帮助你以最少的投入编写质量足够好的代码，从而提高研究效率。我们延续了提升科学工作者软件能力的传统［2—4］，也以本系列此前的文章为基础；那些文章分别关注让科学软件更稳健［5］、易用［6］、可复现［7］、开放［8］和有效［9］。

这些规则来自我们开发科学软件的个人经验，以及过去十年应用于各种计算生物学项目的工业软件方法［10—14］。我们发现，工业界的许多做法适用于研究，但不能盲目照搬，需要调整。科学软件通常由很少几个人开发，开发者自身也是领域专家，非常熟悉软件需求；相较之下，工业场景往往有大型开发团队，依赖另外的业务专家来界定目标。因此，我们挑选出工业软件工程实践中最有帮助的部分，以精炼形式介绍给你。

计算生物学应用对软件工程的要求差别很大（图 1）：一端是利用现成工具和软件包进行日常数据分析的简单脚本，另一端是复杂的通用框架［15—17］，试图自动化并简化广泛的计算任务。刚开始学习编程的读者可参阅文献［18］；开发大型通用科学计算框架的读者，可参阅软件工程文献［10—14］。

> 图 1：计算生物学中科学软件工程的三个层级。第 1 层：使用现成工具和软件包进行生物数据分析的小脚本或程序。第 2 层：自行实现数据处理或计算方法、通常涉及方法实验或创新的研究代码——本指南适用于这里。第 3 层：通用科学计算框架，例如 Galaxy、scikit-learn、pandas。

我们的建议面向已经会写代码、正在开展聚焦型科学项目的研究者，这类项目需要试验计算方法和／或数据处理方法。全文假定读者熟悉 Software Carpentry 的基础概念［4］，例如版本控制［19］和数据管理［20］。

## 规则 1：编码之前先思考

> “我常说，准备理应占任何事业的三分之二。”——阿梅莉亚·埃尔哈特

计算机编程充满细节和决策，在进入之前先弄清自己的处境很有帮助。你为什么写代码？代码怎样帮助你实现科学目标？一个想法刚出现，你可能就想马上动手，因为编程让人觉得自己正在产出东西。但一直忙着做事，并不一定意味着做的是正确的事。

如文献［9］所建议，开始写代码前，尽量获得相关信息。这包括查阅即将使用的计算方法及应用领域的文献，以及搜索项目可以利用的现成软件实现。也应考虑团队或社群中其他人的专长，以及是否有能够帮助项目的潜在合作。把相关信息整理为草图、思维导图、维基或清单，方便经常查看全貌。几小时的文献阅读或与同行讨论，可能省下几周的编程，不能低估。充分了解研究主题和从事相关研究的人，也能帮助你作出更好的技术决策，得到更简单的软件设计，并把精力放在合适的地方。

如果处理数据集，尽早了解数据的优点与局限。特别是数据由合作者采集时，他们可能掌握你还不知道的重要情况。我们建议先用简单的探索性方法开始分析，例如汇总统计、直方图和成对关系图，快速获得整体印象。这些信息有助于与合作者讨论，也能指导后续分析。

## 规则 2：从原型开始，以短开发周期扩展

> “做最简单、但有可能奏效的事。”——肯特·贝克

研究项目像初创企业，往往依赖一组关键假设。例如，典型的方法改进项目假定现有方法还有改善空间；应用型项目则假定可以从某些数据的分析中得到值得发表的解释。在投入过多时间精力之前，尽早检验这些关键假设很重要。在计算领域，可以通过原型技术做到这一点。

创业文献［21］推荐最小可行产品（MVP）：按所需投入衡量，这是检验项目关键假设所需的最小程序。这类原型能以尽可能少的时间投入提供有价值的信息，让你判断研究项目是否值得按原方向继续，还是应该修改或放弃。如果值得继续，原型便可成为后续开发的基础，也能帮助你深入了解所处理的数据、方法和技术。

在原型阶段，你可能想为未来预先多做几个功能。但应避免这样做（图 2）：准备未来的最好方式，是把当前需要的代码写得尽可能清晰、直接［13，22］。为了保持原型简单，应复用现有工具和库（见规则 3），并建立模拟对象（mock）［23］，模拟那些目前还不必编写的代码的输出。模拟代码以后随时可以替换为完整实现。此时采用 Python 或 R 等高级语言也很有帮助：相比低级语言，你可以用更少代码、更快完成原型。

> 图 2：围绕目前真正要回答的核心问题，把原型缩到最小；避免猜测未来的需求并提前实现。漫画左边是装着火箭和机械臂的复杂车辆，标为“你以为会需要的原型”；右边是简单拉车，标为“你实际需要的原型”。

完成原型后，评估自己学到了什么，再据此决定下一步。此后，我们建议以短周期继续开发，聚焦当前最需要检验的关键假设。每个周期开始时，计划实现下一目标所需的最少代码；结束时，严格评价结果，并取得决定下一步所需的信息。短周期让你频繁重新评估处境，保持正确方向［21］。

## 规则 3：寻找代码复用的机会

> “用代码行数衡量编程进度，就像用重量衡量飞机制造进度。”——比尔·盖茨

复用现有代码，是缩短开发时间、快速获得可工作方案的有力办法（图 3）。复用有许多形式：导入并使用现有库、运行现有工具、复用自己的代码（见规则 9）、克隆并扩展既有代码库，或者只是复制别人写的短代码片段。它们都可能省下数小时的开发。除了立即节省时间，复用还能将相关维护集中起来或交给外部，未来继续节省时间精力。例如，使用 scikit-learn［16］这类知名软件包的功能，而非自行开发，你可以相当有把握地预期：这些代码在未来几年很可能持续改进并得到充分维护。

> 图 3：理想的计算研究项目大量复用已有代码，只用少量新增代码实现值得发表的创新。

人们天然更信任自己的代码，而不是别人写的代码。走向极端，就可能出现“非我发明”综合征［24］：不理性地偏爱自制方案（图 4）。虽然使用自己写的东西可能更自在，但应记住：成熟且经常更新的代码库，通常凝结了无数小时对细小问题和边界情况的处理；其中一些问题你甚至还没意识到。它们也包含共同排除复杂错误的努力。因此，复用高质量代码库，能让你避开别人已经解决的错误与陷阱。

> 图 4：“非我发明”综合征。医生伸手提供帮助，旁边的人却守着自己的药锅说：“不，我更喜欢自己做……”

另一方面，自己实现算法也是扩展知识的极好方式，尤其在可以与现成参考实现比较时。自行编写还可以避免外部软件包的依赖问题，也就是所谓“依赖地狱”。所以，要权衡外部软件包的好处与预计的依赖管理工作量。幸运的是，R 的 Packrat、Python 的 pipenv 等现代依赖管理工具，让这项工作比过去容易得多，可以更放心地使用外部包。

浏览文献、在线搜索、与同行或其他专家交流，都能发现复用机会。评估外部库或工具时，要考虑安装、集成所需的工作量，也要检查它所依赖的假设是否适用于你的情况。较大的用户群体和近期开发或更新，是质量的良好信号。不过，即使工具或库并不完全合适，项目早期也可能值得用它来推进工作；以后可以再换成更好的。

## 规则 4：将代码模块化

> “编程的艺术，就是组织复杂性、驾驭纷繁，并尽可能有效地避免其产生混乱的艺术。”——艾兹赫尔·迪杰斯特拉

模块化是把代码组织成可复用、可参数化组件的过程。即使你想快速编码，它也值得做：它有助于防错，让代码更易读、易测，并通过复用避免不必要的重复（图 5）。经过练习，再掌握一些原则，模块化可以成为习惯，而不会拖慢编码。

> 图 5：设计不良的代码库很难处理。漫画把它画成充满机关的金字塔，标出过度复杂的设计、程序错误、过长函数、隐藏依赖、重复代码和含混的变量名。通过模块化避免迷失在代码中，并减少程序错误。

好的起点是遵守 DRY（不要重复自己）原则［10］：避免不必要的代码重复。用可复用函数替代重复代码，还会使代码更易读、更具通用性（［12］第 7 章）。一个简单经验是，不要让函数长到超过一屏。这有助于让函数容易管理，并聚焦某项具体任务。拆分大函数有时需要思考，但形成习惯后，就能以很少投入得到更简单的设计。

如果使用 Python 或 C++ 等面向对象语言，还可以用类进一步模块化。简单做法是先写过程式代码，再把相关变量与函数归到类里。这样使用面向对象，可以封装技术细节、更好地管理复杂性，并更容易跨项目复用代码。除了组织函数和变量，还可以利用多态、继承、对象组合和设计模式［25，26］，构造更复杂的面向对象代码。这些策略支持灵活且运行时行为高度动态的代码。

不过，面向对象程序始终有过度设计的风险，可能产生难以理解和修改的过分复杂代码。为避免这一点，应先尝试消除复杂性，再考虑用高级面向对象策略管理它。明确自己要实现什么，记住科学目标。也应考虑基于低层循环与数组的程序的优点：它们可能比面向对象代码更简单、更快。

如何把代码组织为函数和类，就形成了代码的高层设计。我们建议让设计随着编码演进：需要时再添加函数和类，而不是预先设计好一切。做得恰当时，这种随需而定的设计过程非常高效，只提供真正需要的模块化（［13］第 17 章），从而防止过度设计。此外，“完美”设计可能很费时，常常要求多次重写既有功能。对多数科学应用，尤其原型而言，“足够好”的设计就够了（［10］第 1 章）。

## 规则 5：避免过早优化

> “过早优化是万恶之源。”——唐纳德·克努特

处理大型数据集越来越常见，程序运行也可能因此大幅变慢。在这些情形以及其他代码运行缓慢的情形下，你可能想通过优化提高效率。但优化有风险：耗时、可能破坏代码，也可能为了加速而让代码更复杂或更专门化（图 6）。优化前，应考虑替代办法。

> 图 6：像躲避瘟疫那样，避免过早优化。漫画是一辆困在狭小孤岛上的赛车：速度很快，却没有施展空间。

最好的替代办法，是缩小计算或数据规模。处理大型数据集时，尝试抽取子样本，或换成更小的数据集。研究早期，小型合成数据集常常是最好的选择。只有确认代码确实完成了你想做的事之后，再扩大输入数据。那时你也可能发现，大型数据只需分析有限几次，因此漫长运行时间其实可以接受。

另一个好办法，是让耗时程序运行时，自己去做其他事。如果要跑几小时，就趁机阅读最新论文；如果要一两天，可以安排在周末，或在高性能计算集群上运行。你的时间比计算机的时间更宝贵；要用自己投入优化的时间交换计算机运行时间，应当有充分理由。

如果最终决定优化，值得先做性能剖析，找出运行缓慢的关键位置。剖析时，确保输入足够大，因为某些算法只有达到一定问题规模才会变得低效。先寻找容易实现的算法改进，即用更好的算法减少运算次数。优化之前，想好怎样测试，确保没有引入错误；优化较复杂时，应使用自动化单元测试（见规则 6）。如果采用 Python、R 等高级语言，而瓶颈处又没有更好的算法，可以考虑 C 等低级语言。先找已有的低级代码封装，只有最后才考虑自己实现。

## 规则 6：为关键组件编写自动化单元测试

> “比起执行测试，设计测试本身是已知最好的防错手段之一。”——鲍里斯·拜泽

单元测试是一小段代码，用来检查某个函数在给定预设输入时，是否产生预期输出。它被视为软件工程的最佳实践［27］，因为它能让未来的开发者——包括你自己——快速、自动地检查更新有没有破坏代码。

单元测试在探索性、实验性的科学编码中也有重要价值。研究重点变化时，代码也会随之改变，可能不经意间引入错误。你不会希望仅仅因为“快速而粗糙”的代码错误地报告几乎没有信号，就放弃一个好的研究方向。反过来，因编程错误而报告有缺陷的结果，也是糟糕的科学，过去已造成论文撤稿［1］。单元测试能帮助避免这些问题：功能一被破坏，就及时让你知道，避免酿成后果。

简单的入门方法是“测试先行”：在实现实际功能的代码之前，先设计测试。具体来说，写函数之前，先写一小段代码，用测试数据调用这个函数。再添加 assert 断言，检查输出是否符合预期条件，就能将其变为自动化测试。图 7 展示了例子。有用的单元测试应当简单、运行迅速，并在失败时给出明确无歧义的错误信息。随机测试数据应以一致的种子固定下来，避免测试结果随机变化。

> 图 7：用“测试先行”编写自动化单元测试。目标函数计算 DNA 序列的反向互补序列，并且不区分大小写。A：先写测试和函数骨架，初始测试失败。B：再补全反向互补函数，完成后应通过测试。原图代码转录见下方。

编写和维护测试也需要投入。因此，我们建议把测试集中在那些出错后会影响科学结论的关键代码上（图 8），而非按工业界最佳实践测试一切。例如，P 值计算错误可能是严重问题，而进度条出错则相对无害。数值优化方法和偏微分方程求解器，就是应当自动测试的代码。幸运的是，优质开源科学软件包使许多关键计算能够交给项目外部的代码完成，项目中只剩少量函数需要单元测试验证。

> 图 8：典型计算研究代码组成的示意饼图。大部分是使用现成工具处理数据、调用标准开源包和数据可视化；小部分是需要自动化单元测试的关键计算。识别这些组件，为它们编写自动化单元测试，防止潜在错误。图中未提供实测比例。

如果项目较大、组件较多，也可能需要把多个组件组合起来自动测试，检查它们如何交互。这称为集成测试。根据项目和个人习惯，编写较高层的集成测试，可能比低层单元测试更方便。若要获得最大程度的保护，就两种都用。

## 规则 7：经常重构

> “一盎司预防，胜过一磅治疗。”——本杰明·富兰克林

现代软件开发方法已接受目标和需求频繁变化，推荐让软件系统迭代演进，而非执行预先规定、无法灵活改变的计划［14］。其结果之一，是需要经常重构：在不改变代码外部行为的前提下，改变软件系统、改善内部结构［22］。经常重构可以让设计保持简单、适合用途，避免不必要的复杂与重复。这有助于防错，也方便未来修改系统。

对某些科学工作者，经常重构可能要求过高。毕竟研究目标是科学，而不是编码；系统没有坏，为什么要修？但需求频繁变化，是许多研究项目的共同特点；复用也比不断从头开始更高效。最重要的是，花几分钟重构，可能省下未来几小时的调试。因此，如果你发现调试和管理代码耗时过多，应考虑更频繁地重构（图 9）。

> 图 9：代码改进的理论示意模型。横轴为调试小时数，纵轴为重构小时数；曲线左端标为“过度完美主义”，中间弯折处标为“有生产力”，右端标为“你会在完成之前发疯”。重构能减少调试，而且更有趣，但也会做过头，需要找到平衡。这是示意，不是实验测量曲线。

入门的好办法，是查看“代码异味”清单，即不必要的复杂、可以简化的代码的常见特征（［12］第 24.2 节）。例如重复代码、过长函数、过长参数列表，或代码库不同位置必须同步修改。许多异味可以用工具自动发现［28］，帮助你编程。尤其要警惕：原本为某个目标开发的代码，后来被改作其他用途；最初假设可能已不适用，需要通过重构从软件中去掉。

要成功重构，应聚焦不容易破坏代码或引入错误的小改动。例如改善变量命名、把全局变量改成函数局部变量、消除明显重复、把大函数拆成小函数、把相关函数归入类，以及把函数和类重新组织到适当文件中。这些改动几分钟就能完成，不会明显拖慢编码。经常做少量重构，还能避免未来更大、更危险的改动。如果确实需要大改，自动化测试就很有帮助：它能迅速告诉你重构是否破坏了什么。最后，务必使用版本控制，这样重构出了问题，仍可以返回最近能工作的版本。

## 规则 8：给程序员写自解释代码，给用户写 README

> “代码仅仅能工作，还不够。”——罗伯特·C. 马丁，《整洁代码》

代码文档是供人阅读的程序信息，不参与程序执行。它可以是用户手册、代码示例说明等外部文档，也可以是代码层的信息，即代码本身和行内注释。研究早期的实验阶段，代码库变化很多，因此我们建议先坚持代码层文档，而不是创建外部文档，因为前者更容易与改动保持同步。

大多数有用的代码层信息，就包含在代码本身。采用良好结构、清晰的变量与函数名、用命名常量替代字面数字，并尽量降低控制流与数据结构的复杂度，可以最大化这些信息（［12］第 32 节）。所以，通过重构改善代码（规则 7）也是一种文档工作。与其用大量文档解释复杂代码，不如直接简化代码。

为提高可读性，可以模仿人的句子：用动词给函数命名、名词给变量命名，布尔变量以 is 开头。图 10 对比了糟糕与自解释的代码风格。不要害怕长名称；大多数现代编辑器都有自动补全及查找替换，使用长名称并不困难。

> 图 10：Python 代码对照。A 的风格不好，带有不必要的注释；B 更能自行说明含义。原图代码转录见下方。

图 10A：不好的命名和不必要的注释。

```python
def run(string):
    """接收一个序列，返回其反向互补序列的函数。"""
    # 将碱基映射到互补碱基的字典
    comp = {"A": "T", "C": "G", "G": "C", "T": "A"}
    other_seq = ""
    # 遍历每一个碱基
    for tmp in string:
        # 找到该碱基的互补碱基
        c = comp[tmp]
        # 将互补碱基添加到新序列
        other_seq += c
    # 返回反向序列
    return other_seq[::-1]
```

图 10B：用有意义的变量名、函数名让代码自行说明。

```python
def reverse_complement(sequence):
    base_complements = {"A": "T", "C": "G", "G": "C", "T": "A"}
    complement_sequence = [base_complements[base] for base in sequence]
    return "".join(complement_sequence[::-1])
```

〔译注：图 10 是命名风格对照，不是图 7 的完整解答；这里的实现未处理小写输入。代码逻辑按图保留，不能拿它直接声称满足图 7 的大小写要求。〕

是否使用行内注释，是个人选择；理想情况下，代码应能自行说明。如果使用注释，应解释意图或概括代码，而不是重复代码已经包含的信息（［12］第 32 节）。一个技巧是先用伪代码写算法，再实现为代码。伪代码注释能帮助整理思路，未来更新代码时，也能指引程序员找到相关部分。

还可以引用已发表论文、技术手册等外部文档，进一步减少文档工作量。实现数学公式和算法时，这尤其有用。此时尽量保持变量名与外部参考一致，并在行内注释中写明出处和相关算法、公式的位置。这样既减少需要编写的文档，也能使用 x、y 等短变量名，让代码读起来像数学公式。

当计算实验或分析已稳定到可发表状态时，你可能想公开部分代码，与其他研究者分享。这时改动应当减少，值得为不愿读代码层文档的最终用户准备基础外部文档。README 是最快的方法；GitHub 等代码托管服务通常会在仓库页面自动显示它。README 应包括用途说明、安装步骤和简单使用实例，帮助用户上手。

## 规则 9：让库与工具从研究中自然生长

> “当一个人凝视一堆石头，心中怀着大教堂的形象时，那堆石头就不再只是一堆石头。”——安托万·德·圣埃克苏佩里，《小王子》〔引语出处按原文保留〕

计算研究项目中，你通常会编写代码来完成任务、解决问题。其中一些也许对其他研究项目有用，值得保存供未来使用。长期来看，这是极有力量的策略：复用过往项目的成果，可以帮助你形成一个能快速、高效开展研究的专长领域。

因此，我们建议把代码分为项目代码和库代码。项目代码回答特定研究问题，库代码则包含当前和未来项目可复用的组件。这样能简化研究代码，把数据处理与预处理等技术任务移交给库。你也可能需要维护一组工具，即提供用户接口、执行实际任务的程序，例如数据格式转换。把库中的适当函数连接到用户接口，就常能快速形成工具。多数情况下，我们推荐命令行而非图形界面，因为命令行技术上更简单，也容易通过自动化脚本将工具串起来。

库代码的质量要求高于项目代码。研究项目不确定，生命周期通常有限，库却需要长期维护。构建库时，应考虑所依赖的软件包将来变化的可能性，它们可能迫使你进行维护。为了准备这些变化，要坚决消除重复代码，让未来更新更简单、较少出错。也应考虑为库中较关键的组件编写自动化单元测试［27］。

鉴于库的质量要求更高，我们建议谨慎选择纳入库的代码。不要在研究项目之前先造库，因为你很难预测哪些组件值得复用。应让库从研究项目中自然生长：组件证明了自己的价值，再移入库。例如，如果两个研究项目都在编写同一个类，可以把它移入库，再由项目使用库。这样构建库，就只需维护真正需要的代码。

## 规则 10：大胆探索，发表时务必严谨

> “大海危险，风暴可怕，但这些障碍从来都不足以成为留在岸上的理由。”——费迪南德·麦哲伦

本指南的规则，旨在让你通过高效编程，在不确定环境中探索计算想法。从心理上说，在想法证明价值之前限制投入，可以避免沉没成本谬误［29］：不是因为事情值得做，而只是因为已投入资源，就继续做下去。检验一个想法所花时间精力越少，越容易修改它，或放弃它，转向更有成果的方向。

与此同时，编程速度必须与质量结合，避免误导性的错误、错误科学结论和不可复现的结果。项目早期可以快速、粗糙一些，发表时则必须保证质量和可复现性［7］。特别是在探索阶段结束、已经得出结论之后，应有脚本化的计算流程，复现每一项拟发表结果。这些脚本可以用 shell 编程（Bash）、计算笔记本（例如 Jupyter［30］）或 Nextflow［31］、Snakemake［32］等工作流描述语言编写。最后，至少要确保结果不含编程错误，并符合所在领域的标准。

## 结论

形成快速编程、同时产出高质量代码的风格，是终身的功课；我们的规则只是起点。要真正熟练，需要亲自试验，了解什么对自己有效。希望把这些建议融入编程风格，能帮助你成长为计算生物学研究者，更有能力应对本领域的科学挑战。
