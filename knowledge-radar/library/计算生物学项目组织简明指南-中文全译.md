## 引言

大多数生物信息学课程重点讲授算法，也许还会安排一些内容，教学生编程技能和使用现有的生物信息学软件。遗憾的是，对准备从事研究的学生来说，这样的课程并没有涉及开展计算实验时每天都会遇到的许多组织问题。实际工作中，怎样组织和记录计算实验，常常是边做边学；这个学习过程受到个人偏好以及偶然与合作者、同事交流的强烈影响。

本文旨在描述一种开展计算实验的良好策略。我不会讨论怎样提出假说、设计实验或得出结论这些深层问题，而是关注一些相对琐碎的事情，例如组织文件和目录、记录进展。它们之所以重要，是因为糟糕的组织选择会明显拖慢研究进度。我并不声称这里概述的策略是最优的。这些原则和实践，只是我在十二年生物信息学研究中逐步形成的做法，也吸收了与我讨论过这些问题的其他研究者的建议。

## 原则

核心指导原则很简单：一个不熟悉你项目的人，应当能够查看你的计算机文件，详细理解你做了什么，以及为什么这样做。

这个“人”可能是各种各样的人：读了你的论文、想尝试复现工作的人；想了解实验细节的合作者；在你已经换工作后，希望继续扩展你成果的实验室后来的学生；或者想了解你的工作、评估你研究能力的导师。不过，最常见的情况是，这个“人”就是你自己。

几个月后，你可能已经不记得，创建某一组文件时自己在做什么，或者当时得出了什么结论。于是，你要么花时间重建先前的实验，要么丢失从那些实验中得到的认识。

由此得到第二个原则，它其实更像墨菲定律的一个版本：你做的每件事，很可能都得再做一遍。你难免会发现待分析数据的初始准备有缺陷，或者得到新数据，或者认为某个模型的参数探索范围还不够广。这意味着，上周做过的实验，甚至过去一个月一直在做的一整组实验，很可能都需要重跑。如果工作组织得清楚、记录得充分，用新数据或新参数重新做实验，就会容易得多。

要了解这两个原则怎样落地，我们先来看一个项目的目录和文件组织。

## 文件与目录组织

开始一个新项目时，你需要决定相关目录采用什么组织结构。一般来说，把同一个项目的所有文件放在一个共同的根目录下，是个好主意。例外是多个项目共用的源代码或脚本：这样的每个程序可以有自己的项目目录。

在一个项目内部，我在顶层按逻辑组织，下一层按时间组织，再下一层又按逻辑组织。图 1 展示了一个叫作 msms 的项目。多数项目的根目录下，我会设立 data 目录保存固定的数据集，results 目录跟踪基于这些数据进行的计算实验，doc 目录按每篇论文各设一个子目录，以及 src 等源代码目录和 bin 等已编译程序或脚本目录。

在 data 和 results 目录内部，人们常常也想沿用类似的逻辑分类。例如，你打算用两三个数据集对算法做基准测试，就可以在 data 下为每个数据集建立一个目录。根据我的经验，这种方法有风险，因为最终整组实验的逻辑结构，可能与最初设计的样子截然不同。

results 目录尤其如此：你甚至可能事先不知道需要开展哪些类型的实验。如果试图给目录起逻辑性名称，最终可能得到一长串目录，而六个月之后，你已经不知道这些名字该怎样解释。

相反，我发现按时间组织 data 和 results 目录最合理。事实上，采用这种做法之后，区分 data 和 results 可能也没有用处了。不妨设想一个叫作 experiments 的顶层目录，下面是 2008-12-19 这样的子目录。也可以在目录名中加上一两个词，说明其中实验的主题。

实际工作中，一个实验往往不止做一天，因此你可能连续工作几天甚至更久，才创建新的子目录。日后，你或别人想知道你做了什么时，工作的时间顺序就会一目了然。

单个实验目录内部的文件和目录按逻辑组织，具体取决于实验结构。很多简单实验可以把所有文件放在当前目录。如果文件开始变多，就应当引入一些目录结构，存放不同类型的文件。通常，这种目录结构会由下文讨论的驱动脚本自动生成。

## 实验笔记

与上述按时间组织的目录结构并行，我发现维护一份同样按时间组织的实验笔记很有用。这份文档位于 results 目录的根部，详细记录进展。笔记条目应注明日期，而且应当写得比较详尽，通过链接或嵌入的图片、表格展示所做实验的结果。

除了准确描述做了什么，笔记还应记录观察、结论和未来工作的想法。尤其在实验结果不理想时，人们很容易只链接最终图表，便开始新的实验。在这样做之前，务必记录你是如何知道实验失败的，因为别人读你的实验笔记时，未必能明显看出结果应当怎样解释。

除实验的主要描述文字外，把交谈笔记和电子邮件文本也转录进实验笔记，往往很有价值。这些条目能提供项目随时间发展的完整图景。

实际工作中，我要求研究组成员把实验笔记放到网上，必要时设置密码保护。与实验室成员或项目团队会面时，我们可以参照在线实验笔记，聚焦当前条目，同时按需向上翻阅先前的条目。还可以把网址提供给远程合作者，让他们了解项目进展。

如果不想自己搭建“土制”的电子笔记系统，也有其他选择。例如，已有多种商业软件帮助科学家创建和维护电子实验笔记 [1–3]。此外，尤其在协作场景下，把实验笔记放在维基系统或博客网站上，也可能很有吸引力。

## 开展单个实验

现在，你已经建立了目录结构，并为当前数据创建了一个目录，打算在里面开展某个实验。接下来怎么办？

总原则是：记录你执行的每项操作，并尽可能让它们透明、可复现。实际做法是，我会创建一个 README 文件，保存开展实验时使用的每条命令行；或者创建一个驱动脚本——我通常叫它 runall——自动完成整个实验。这里的选择很大程度上取决于你偏好的开发环境。

如果使用 Matlab 或 R 这样的语言，也许可以把所有操作保存在该语言的脚本中。如果使用编译型代码，就需要另外保存命令行。我个人混合使用 shell 脚本、Python 和 C。这三者怎样搭配，取决于实验的复杂度。不管怎样选择，最终都应有一个与实验笔记条目相对应的文件：实验笔记用文字描述实验，驱动脚本则保存全部繁琐细节。

开发驱动脚本时，我尽量遵循以下经验规则：

1. 记录执行过的每项操作。
2. 多写注释。驱动脚本一般没有多少复杂逻辑，却常常调用你写的各种脚本，以及一组可能五花八门的 Unix 工具。因此，对这类脚本，一个合理的经验标准是：别人应该仅靠读注释，就能理解你在做什么。注意，我并没有主张编译型代码或更复杂的脚本也必须采用某种特定注释方式；怎样正确写这类注释，存在许多不同观点。
3. 避免手工编辑中间文件。否则，脚本就只是半自动的：下次运行实验时，还得重新做一遍手工编辑。许多简单编辑操作可以用 sed、awk、grep、head、tail、sort、cut、paste 等标准 Unix 工具完成。
4. 把全部文件名和目录名集中保存在这个脚本中。如果驱动脚本调用其他脚本或函数，就由驱动脚本把文件名、目录名传给这些辅助脚本。强制把它们集中在一处，会更容易跟踪和修改输出文件的组织方式。
5. 访问同一个项目内的其他文件时，使用相对路径。若使用绝对路径，别人把项目检出到自己的本地目录后，脚本就不能正常工作了，详见后面的“版本控制的价值”。
6. 让脚本可以重新启动。我发现，把耗时步骤放在“如果输出文件不存在，就执行操作”这样的条件结构中很有用。如果想重跑实验的某些部分，就删除对应的输出文件。

对运行时间很长的实验，我希望随时能得到当前进度摘要。在这种情况下，我创建两个驱动脚本：runall 运行实验，summarize 汇总结果。runall 的最后一行调用 summarize，由后者生成概括实验结果的图、表或 HTML 页面。summarize 要写成能处理部分完成的实验，从而展示计算目前完成了多少。

## 处理与预防错误

开发一组复杂实验时，你会在代码中引入错误。这不可避免。但如果错误难以追踪，或者更糟，你根本不知道它存在，并据此得出无效的实验结论，问题就尤其严重。下面是三条错误处理建议。

第一，编写健壮的代码来检测错误。即使只是简单脚本，也要检查不合理参数、无效输入等。只要可能，就用健壮的库函数读取标准格式文件，不要临时编写专用解析器。

第二，一旦发生错误，就中止。我通常让程序向标准错误输出信息，然后以非零退出状态结束。这样的行为看起来可能让程序很脆弱；但如果跳过有问题的情况，继续实验的下一步，你就有可能永远注意不到这个错误。由此还可以推出：代码应始终检查所执行命令和所调用函数的返回码，一旦发现失败就中止。

第三，只要可能，就先用临时名称创建每个输出文件，等文件完整生成后再重命名。这既方便实现脚本重启，更重要的是，避免把部分结果误当作完整结果。

## 命令行、脚本与程序之间的取舍

规划和执行一系列计算实验时，最常遇到的设计问题，是应在软件工程上投入多少精力。根据个人性格，你可能想迅速执行几条命令，立刻检验假说；也可能想过度设计程序，把实验自动化得漂漂亮亮。

实际工作中，我发现两者之间的适当折中，往往是迭代改进脚本。初始脚本只提供最小功能，也不具备从部分完成的实验中间恢复执行的能力。随着脚本功能扩展、使用频率提高，可能需要把它拆分成多个脚本，或从简单的 shell 脚本“升级”为 Python；如果内存或计算需求过高，再从 Python 转为 C，或将两者混合使用。

因此，我写的脚本通常分为以下四类：

1. 驱动脚本。这是顶层脚本，因此每个目录只有一两个。
2. 一次性脚本。这是为单次使用设计的简单脚本。例如，把项目中某个任意格式的文件，转换成现有脚本能使用的格式。这类脚本与调用它的驱动脚本放在同一目录。
3. 项目专用脚本。这类脚本提供一个项目中多个实验都会用到的通用功能。我通常把它们放在项目根目录下的一级子目录，例如图 1 中的 msms/bin/parse-sqt.py。
4. 跨项目脚本。有些功能通用到可以用于许多项目。我维护了一组这样的通用脚本，用于从 FASTA 文件提取指定序列、生成 ROC 曲线、为 n 折交叉验证划分文件等。

不论脚本打算通用到什么程度，都应当有清楚的接口文档。尤其是，每个脚本或程序，不管多简单，都应能输出比较详细的用法说明，讲清楚输入、输出和可用选项。

## 版本控制的价值

版本控制软件最初是为维护和协调复杂的软件工程项目而开发的。Subversion 等现代版本控制系统以中央仓库为基础，保存一组相关文件的全部版本。多人可以把这些文件的工作副本“检出”到本地目录，修改后再把变更提交回中央仓库。

我发现，版本控制软件对管理计算实验非常有价值，原因有三个。

第一，它提供了一种备份。虽然我们大学的计算机系统每晚都会自动备份，但我笔记本电脑的备份安排没有那么规律。而且，不小心覆盖文件后，从 Subversion 找回昨天的版本，通常比给系统管理员发邮件更容易。一位研究生甚至告诉我，每次敲完 svn commit 都会松一口气，因为这条命令把工作目录的快照存进了中央仓库。

第二，版本控制提供历史记录，有助于追查错误或理解旧结果。通常，脚本或程序会在项目进行中持续演变。我不保存许多名称略有不同的脚本副本，而是依靠版本控制系统跟踪版本。如果要精确复现三个月前的实验，就可以检出项目在当时的状态。注意，大多数版本控制软件还允许给仓库某个状态加上逻辑“标签”，便于之后找回。

第三，也许最重要的是，版本控制对协作项目极其有价值。仓库让合作者能够同时处理一组文件，包括脚本、文档和论文草稿。两个人并行编辑同一文件时，版本控制软件会自动合并两个版本，并标记双方都改动过的行。临近截止时间的几个小时里，我一边和远程合作者通电话，一边一起编辑同一文档、每隔几分钟提交一次变更，并不少见。

版本控制的基本思想看似简单，但要有效使用 Subversion 这样的系统，仍需要自律。

首先，版本控制只有经常使用才最有用。一条好的经验规则是，至少每天提交一次变更。这样既保证历史记录完整，也保证意外覆盖文件时总有较新的备份。如果正在修改代码，导致原来能编译的程序暂时不能工作，可以提交到项目的一个“分支”，明确表示它还在开发中。新功能完成后，再把分支合并回“主干”。只有到这一步，变更才会传递给项目组的其他成员。

其次，版本控制只应用于你手工编辑的文件。自动生成的文件，不论是编译好的程序还是计算实验结果，都不应纳入版本控制。这些文件往往很大，提交它们会浪费磁盘空间：不仅仓库和每个工作副本都会保存一份，而且反复重跑实验时，这些文件通常也会不断变化。二进制文件尤其浪费：由于版本控制软件按行操作，二进制文件的版本历史就是所有版本的完整副本。这个规则也有例外，例如实验期间不会改变、体积相对较小的数据文件，但这样的例外很少。

不提交自动生成文件有一个实际麻烦：每次执行更新命令，版本控制软件可能都会对工作目录中这些未提交的文件发出提示。为了避免每次更新都要翻过好几屏文件名，Subversion 和 CVS 提供了忽略指定文件或文件类型的功能。

## 结论

上面许多思想，以前已经在计算生物学或一般科学计算的语境下得到过讨论。尤其是，在科学软件开发中采用稳健的软件工程原则与实践的必要性，已经有大量论述。例如，Baxter 等人 [4] 为科学软件项目提出了五项“最佳实践”，Wilson [5] 则介绍了多种能让计算科学家工作更轻松的标准软件工程工具。

虽然上述许多实际问题普遍适用于各种科学计算研究，但与生物学家和生物数据打交道，也有一些特殊问题。例如，许多生物数据集存放在中央数据仓库中。对比较简单的数据集，在实验笔记中记录网址、版本号和下载日期等基本信息，也许已经足够。但面对特别大或不断变化的数据，可能需要更复杂的方法。例如，Boyle 等人 [6] 讨论了科研项目中怎样更好地管理复杂数据仓库。

此外，为了让湿实验生物学家能够获取并理解结果，项目管理也会受到实际影响。例如，为了让结果更容易理解，可能需要在实验笔记的文字描述上投入相当精力，而不能仅仅放一张图或表，再写几行主要结论。更具体地说，操作系统和软件差异也可能带来协作上的麻烦：计算机科学家可能喜欢用 LaTeX 排版语言写文档，生物学家则可能偏好 Microsoft Word。

正如引言所说，我希望本文更多是在描述，而不是在规定。尽管希望其中一些做法能对许多读者有用，但最重要的信息是：如何高效地开展准确、可复现的计算实验，其组织与实施本身就值得认真思考和讨论。许多相关主题没有在本文涉及，包括良好编码实践、实验自动化方法、怎样根据实验结果撰写论文等。因此，我鼓励感兴趣的读者通过 PLOS Computational Biology 网站提出评论、建议和批评。
