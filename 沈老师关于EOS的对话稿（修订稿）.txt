回到我们部门以及全公司的工作。IT 有双重角色：既有施工队的角色，也有产品部的角色。未来，我们要构造一套方法论，以及承载这套方法论的产品，帮助所有业务做变革。说得好听叫变革，说得难听就是提效。提效的第一件事是什么？替代人的重复工作。人的重复工作不仅低效，而且容易犯错，也没有传承。今天如果让张猛每天干同样的事情，换一个人又要从头学、从头干，张猛踩过的坑还要从头再讲，就没有形成投资积累，效率也毫无提升。

所以，我们所做的一切都是为了组织变革，也是为了大规模地实现人的工作智能化。组织真正提效以后，还会不会保持现在的规模？有两种可能。一种是对外扩张的速度超过了对内提效的速度，我们的规模可能还会变大，因为战场变大了，我们要去攻城略地，打进以前没有进入的行业。另一种命运是，对外扩张的速度远远低于内部提效的速度，那就一定会裁员。就是这么简单的一道数学题，简单到不能再简单。

什么样的组织，能够把对内提效迅速转化成对外扩张的速度？这就是组织能力。你在内部做了这么多提效，用 AI、用各种工具、做各种小变革，每个人每天的代码产出变成原来的十倍，提交量变成原来的几十倍，但组织没有能力把它转化成对外的战斗力，最后反而伤害了自己。老板会说：“你这个提效做得不错，把隔壁老王开了吧。”为什么？因为公司的销售收入没有增长。绝大部分部门，99% 的部门，最终看的都是花销占公司收入的比例，归根结底还是毛利，没有别的秘诀。

大家都能听明白这个数学题。所以到最后，关键是组织用什么样的价值循环网络，把每一个员工的工作转换成组织价值，从而到外面攻城略地，扩张组织的边界和战场。比如海外，比如其他行业，比如向高端进发，或者向低端进发，都可以。

因为没有绝对的好行业和坏行业，只有价值的周转效率：一块钱投进去，什么时候能变成两块钱，是一年以后，还是二十年以后？从这个角度看，不是科技企业就一定好，不是初创企业就一定好，也不是老企业就一定差，就看转化效率。麦当劳的转化效率做得好，也可能是最棒的企业，甚至比我们好。还有很多企业，你甚至没听过它的名字，但它的转化效率比我们高。热点只是在不断变化，不要只看热点。

我们也当过热点，大家都体会过当热点时有多么容易。但是资本市场犀利无比。我们的股价从四十多块钱降到十二块钱，有经营业绩的问题，有市场环境的问题，也有一个很大的因素：我们已经不在热点上，跟 AI 不沾边。你硬凑也凑不过去。AI、具身智能那边同样在血肉搏杀，淘汰也非常快，就像我们 2017、2018、2019 年进入新能源行业时一样。当时中国有近三百家新能源车企，今天还能记得几家？

所以，没有什么好行业、坏行业，好公司、坏公司，只有优秀的公司，也就是周转效率高的公司。初创阶段不太看内部经营效率，更多看天花板有多高。天花板不断拉高时，哪怕经营效率很差，一块钱投进去也可能迅速得到收益。但当天花板出现瓶颈，技术突破也出现瓶颈时，就必须抓经营效率。内部卷、行业卷，把别人卷输，最后只剩头部企业，前五家可能占据 80% 的市场，这就叫 CR5，也就是 Concentration Ratio，行业集中度。

前些年创业时，很多饮料、冰淇淋、快消品、小食品都显得很新鲜、很文艺、很有文化，最后死在哪里？死在供应链，死在开店效率，死在人效，死在坪效，死在库存周转率。最后活下来的，都是把这些效率指标做好的公司。这就是组织能力。道理很简单，但非常关键。

今天在座的很多人都是开发背景，我为什么一定要讲这些？因为已经没有一片净土了。开发人员不能再躲在后面，等着别人给你一张安稳的书桌，除非你自己靠 AI 给自己写。未来所有组织在 Coding 这件事上，都不会再用高薪供养与利润中心、与赚钱相距很远的程序员。这不是开玩笑。每个组织都会非常讲究，你做的工作离利润中心究竟有多远。已经没有人可以永远躲在后面，默默琢磨 RocksDB 会不会比 LevelDB 好一点，或者某种数据结构会不会再好一点。这样的机会已经非常少了。

我们作为公司内部的 IT，首先要认定一点：我们就是组织的数字面。有人会说你是 IT、是企业系统、是一个部门，也对。但我们所做的一切，都是在建设业务的数字世界，引导业务怎样被构造出来。所以，从我的角度看，我的目标应当和公司的主要经营者一致。不管未来 COO 是马哥负责运营，还是翔哥继续在管，这件事都躲不掉。你不可能只卖一些零散资源，那没有意义，谁都可以卖。

各领域也一样，要对准那个领域的数字世界建设。有些领域没有 Sense。没有 Sense 的人，会把你当成外包：你干得像零工，卖得像零售。有 Sense、有 GPO 的人，会把你当成构建业务架构的武器。不同部门的认知水平完全不同，也没有被拉齐，这就导致整个组织的价值传递没有那么高效。

比如一次车型发布。很多人觉得奇怪：为什么外面的人都在对付我们，各种公关动作都在做，而我们好像不知道该干什么？这里固然有营销、公关预算的问题，但更多是大家不知道那个时候该干什么。一个车型发布完、发布会开完，几个手里握着几十亿资源的部门却站在旁边看，不知道下一步怎么干，因为后续流程没有人驱动。

以前为什么能干？因为以前是李想本人驱动。他亲自关心 L9，每天看发生了什么，很多事情百分之百是他驱动起来的。现在不是了，他有三分之二的精力在第二曲线，只有三分之一在主战场，所以就会出现这种偏差。

解决办法无非两种。第一种，像雷军一样，一号位重新回归主战场、重新穿透；大疆现在也是汪涛重新回到主战场。第二种，不再依赖一号位事无巨细地驱动，而是建立流程制度，把权和利分下去。华为本质上就是这个逻辑，顶层流程的核心是分权、分利。

20 世纪 90 年代，任正非已经五十多岁，身体也不好。他知道所有事务不可能都由自己来办，必须建立机制让别人来办。年轻时总觉得精力无限、天下我有、什么都能自己看，但组织大了就不可能。因此华为形成了分权、分利的逻辑，做出《华为基本法》，明确每一段由谁负责，连 CEO 都采用轮值机制。老任平时很少直接显示权力，主要行使否决权。

所以，每个组织都必须找到符合自己当前阶段的运作方式。在这个过程中，组织要建立自己的价值传递网络，这就是业务架构。说流程，本质上也是在说业务架构。一个公司，小到一个部门、一个三级部门，都必须上下校准，不能只允许底下各自创造、各自闭环。你自己闭环了，但无法翻译、转化成公司的价值标准，哪怕公司注入大量资源，管理者也投入大量管理能量，仍然不能形成有效产出，仍然无法对齐。因为这家公司是三万人一起干一件事。

我那天在会上讲，大道理管小道理。经过一年多时间，做了大量沟通、研究、观察和复盘以后，我想明白一件事：这家公司要么死，要么变，无非两条路。死就是熬死。没有明确目标，或者把目标赌在一个虚无缥缈的地方，指望未来再赢一把，一旦赌输就完了。

另一种是，我可以赌，但基本盘的下限必须高，我不能离开牌桌，我还要有牌可打。组织必须有能力，这就得靠建设，不能靠熬。熬有什么能力建设可言？熬的办法无非是跪着裁人，把花钱多的地方砍掉。这样的逻辑很可能把自己真正有价值的能力也砍掉，就像 2024 年那次，自动驾驶最突出，砍完以后才发现还得再找回来。

我跟实操的 HRBP 洪丹聊过，他说那是他在理想做过最神奇的一件事。我简直无法想象会出现那样的情况。所以大家不用担心同样的事情会再发生，因为那件事的后果已经非常清楚。但这不代表不会换成别的问题。如果投资逻辑想不明白，可能会犯其他错误。

那次事情的二次伤害很大。裁前 10% 的时候，可能还可以从能力和绩效去考虑；但裁到 25% 时，尤其从 15% 到 25% 这部分，我已经明显看到不是这个逻辑了。那时每个部门都一样，大家已经不知道该怎么选，最后变成谁走、谁来守系统。这就麻烦了，因为守系统的人未必是最优秀、最有想象力的员工。最后大家可能靠守着一个系统来增加存在感，整个管理逻辑就错了，最终就是劣币驱逐良币。

所以回到企业智能。我们有施工队的一面，但同时一定要帮助组织学会为自己的业务建模，用数字化为这个模型提供运行基础，让模型能够在数字世界里运转，然后不断提效。这条路躲不过去。要么走这条路，要么干脆不干、大家各自建设。所有简单的路大家都会试，但我看不懂哪条简单的路能成功。全行业都在尝试，谁也不傻。

大疆也算科技企业。创始人的阳光照不到的地方，只要稍微松一点，内部就拉不通，因为它也是制造业，也是 IPD 逻辑。产品力稍微偏一点，供应链稍微差一点，制造稍微差一点，就会出大问题：成本可能差得很远，库存可能积压，门店卖不出去，绩效也说不清。只有创始人全力盯着的产品才有前途。所以他们也意识到，必须把组织从创始人个人驱动改成组织流程驱动，进行分权、分利。

我们有没有意识到？意识到了，但以前没有坚持下来。未来会不会回到这条路？不回去就是死，没有别的选择。这个世界上如果真有简单的方法，早就有人做了。我看过、交流过很多制造企业，大家想尽办法试过各种路径。轻资产行业相对容易一点，比如快消、奶茶，有供应链，但自己不制造，也不压那么大的库存。汽车不一样，一辆车上万个零部件。哪怕一个桌椅厂着一场火，一个月就可能少造四千辆 i6。任何一条供应链都可能出问题。

我们有过一个灯厂供应商爆雷，没钱了，我们得去垫资；它一旦倒闭，我们的产线就会断。你看这个体系有多复杂。所以数字化要管什么？要管一级供应商、二级供应商的财务状况，要管它们上下游的原材料。比如它依赖磷酸铁锂，锂矿又可能依赖其他国家的资源，一旦中间出现国别风险，就可能影响我们的生产。这些东西都应该管起来。

数字世界就是不断迭代，把所有可管、应管、应看的事情纳进来。这样组织才会形成统一感知，应对风险的能力才会急剧提升。比如锂矿周期和锂矿投资，直接决定未来每辆车型的毛利。

我那天和老汤聊一个很有意思的话题。我说 L9 后面不是要出纯电版吗？纯电版有个问题：蔚来卖纯电，有 BaaS 和换电支持；我们虽然有 5C，但没有 BaaS 的金融能力。BaaS 有两个好处：一是电池从车价里拿出来以后，车价低、税也少；二是再叠加较低首付，用户初始购车成本会明显下降。L9 纯电版怎么卖？

他说，纯电版未必比增程版贵。首先，拿掉增程器能省一笔成本；其次，国家对带发动机的车型还会收一部分税，这里也能省下一笔。所以电车的成本溢价有可能被吃掉，单车毛利甚至可能比增程版更高。我说，那就应该把收益让给用户。他说不一定，因为锂矿价格今年上下波动，会让单车收益在亏四千元和赚四千元之间来回震荡。只是一轮正常的小震荡，还不是 2022 年那种锂矿价格的大震荡。

这些东西都要管起来。现在公司内部的信息其实没有贯通，它可能只存在于某些人的感知和个别人的认知里，或者事后才被发现。我们需要把事前的感知能力建立起来。在这样一个复杂的三万人组织中，要做到这件事，就必须构建一整套端到端的方法和工具。方法上，我们用企业架构的方法去做；但还要有一个系统来承载它。

所以，我们为什么要做 EOS？因为我们要做 One System，要减熵。AI 出现以后，从组织角度看存在一个矛盾：组织的熵可能反而增加。我们发布的服务多了一百个，但这些服务互相有关系吗？没关系。因为基层员工做的工作原本就彼此分散。大家拿 AI 做了很多东西，同一种平台我都见过五套，相似但不相同，还有很多业务自己做的东西我根本不知道。大家都在做大量重复建设。

我们需要 One System。大家开发的 Application、数据定义，都要运行在同一个系统中。传统 IT 在今天极其阻碍 AI，极其阻碍 Agent。不要以为给 Agent 一个数据湖、一个宽表就算打通了，没有。治理过程有没有打通？后面的执行系统有没有打通？权限有没有管好？权限没管好，什么功能都不敢开；开了就可能出大问题，因为 AI 的速度比人快一万倍，可能迅速把公司毁掉。

所以这个东西必须是 One System。原来的 IT 系统在当年未必做错了，但放到 AI 时代，今天都错了。Salesforce、SAP 等产品都在努力把自己扩展成 One System，但它们摆脱不了自己原来的命运。昨天微软 MAS 平台的负责人也来聊，他们原来是提供 API、Token 和 Agent 能力，现在也想加配置平台、权限管理，变成更完整的 Agent 平台。他们也想做 One System，但能不能做到，是另一回事。

从人机界面往下打，是打不通的。必须先把底层逻辑做对，再重新生长出人机界面。而人机界面又是未来最容易变化的部分。以前很多系统都是从界面开始做：因为某个人需要一个功能，就先给他开发，其他功能再不断叠加；东西多了以后，再把 IDaaS 之类成本较低的共性能力抽出来。但等到想做全栈抽象时，几年都做不出来。理论研究没问题，实际寸步难行；要么抽象不对，要么抽象出来也没人用。

Agent 时代，人机交互逻辑正在发生深刻变化。很多业务会做一个工作台，因为业务负责人认为，把统计、甘特图、参与人等信息摆在一起，最方便确认和决策。但这是不是 Agent 时代真正的人机交互逻辑？不一定。

比如 Agent 的报告放左边还是右边，定位完全不同。放左边，是左边驱动右边：Agent 负责生产，我在右边确认它是不是我要的。放右边，它就是随时可以折叠的助手，中间才是我的主工作台；我在主工作台完成对齐，遇到不明白的地方再去问右边。放左边的 Agent 是创造，放右边的 Agent 是 Assist，完全不一样。所以未来人机对齐会被重新定义。难就难在，我们现在还不知道哪一种方式最好，只能在业务一线慢慢收敛出来。

昨天晚上发布的 Harley 就是一个很保守的尝试。它不像 Codex 或 Claude 那样，一开始就把界面做得很复杂，而是先搭一个插件框架，尽量不侵入人的对齐工作。它先把变量和框架放到位，再通过对内、对外的同一发布节奏，根据实际需求逐步补产品能力。输入框、工作区、三栏布局，每一个位置其实都是产品设计。这个方向值得研究，因为我们同样面临一个问题：公司的系统是长期增长、组合出来的，未来的人机交互应该怎样重新组织？这是一个非常大的课题。

我们要做 One System EOS，因为单点、分立的系统做得再多，也没有太大的业务价值。未来系统有两个责任：第一，系统本身要支持人机对齐；第二，变革要来自对现实运行的挖掘。我们不能把变革 100% 扣在领导头上，也不能 100% 扣在员工头上。领导要给出大致的变革方向、流程方向和生产关系划分；基层要从底向上梳理真实的工作模式；中间还要依靠系统里的流程挖掘、数据挖掘和异常状态发现。三者相辅相成，事情才能正向迭代。

原来的做法，包括 AI Coding 以后产生的无数服务，不能支持这个变革过程，也不能促进业务从上到下为自己建模，因为所有东西都是散的。你们肯定会把自己手里的工作自动化。程序员都知道一句话：Don't repeat yourself，DRY 原则。同一件事干三遍，就应该自动化。但一旦离开个人认知范围，想和小组同事一起把事情自动化，就难了。两个人共同建立一个模型，把两个人之间的事情拉通，更难。

谁来做这个连接？小组长。因为那是他负责的一段业务，他要主动思考。再往上，还有大组长和更高层负责人。但组织不可能只靠这种自下而上的组合自然形成，因为每个人抽象的维度不同：有人从成本角度建模，有人从项目管理角度，有人从工具角度，有人从每天做什么的角度。每个人的抽象模式都不一样，杀猪杀鱼各有各的杀法。到某一层就对不上了。这时必须从上往下给出统一思路，再让大家共同对齐。

整个过程是反复拉齐的过程，这对系统提出了更高要求。首先，所有东西都应在一个系统里；其次，这个系统要允许分叉、允许变化。什么系统允许分叉和变化？Git。你自己可以维护一个 Git 逻辑，也可以分享给别人；别人有不同意见可以 Fork，做完以后发起 Pull Request，大家一起讨论。主管看到好几个项目以后，可以再往上抽取，形成一个 Mother Repo 或 Father Repo，继续指导其他项目。我们已经看到内部有不少团队这样做。它解决的是去中心化创新与中央治理之间的平衡。

所以回到 EOS，EOS 最关键的功能是什么？Multi-resource Global Branching，也就是多资源的全局分支。这是最有价值的核心。它首先正视了什么叫资源。传统企业系统里通常没有显性的 Resource 概念，也没有 RID 的概念。销售系统、SAP、飞书里，很少把这个概念直接说出来，因为过去不需要，只要把工具做好就行。飞书是工具，飞书文档也是资源，但资源概念并不显性。

为什么在 EOS 或 Foundry 里必须把资源显性化，明确它们属于不同的 Resource Type？因为不同资源要共同完成一些公共任务：它们可能彼此关联，共同承载一种语义、一个概念、一项能力；一部分资源还要进入 Compass 和文件体系；它们要有权限、版本、计划、血缘和审计。这些都要求资源首先具有统一身份。

然后才是为每种资源制造工具链。有些工具直接生产资源，有些工具用于查看和分析资源，最后再把相关资源包装成产品，支持复用、跟踪和治理。这就是 Foundry，也是未来非常有价值的部分。

大家今天做 AI 时会发现，很多情况下只用 GitLab 就够了，甚至飞书都不用。因为 Agent 出现以后，人会寻找成本最低、最容易被 Agent 理解的现有资产。GitLab 里的代码、Issue、Release、权限本身构成了一张图，Agent 可以遍历，人能理解，机器也能理解。飞书和飞书项目也能做一部分，但一到大排期、跨人和跨组织管理，就会很难。

低代码为什么在 Agent 面前价值下降？因为产生代码的成本已经很低了，高码、中码、低码之间的边界在变化。EOS 不是只管理代码，而是要管理大部分企业资产的迭代，包括 Dataset 等资源。理解这一点就好。原来一些低码工作不是没有价值，而是要往上一层挪，扩大管理范围。

做 FDE 时，我们可以先做一个很小的内核，不一定什么都做。可以先做 Global Branching 和资源管理，再逐步补团队需要的能力。然后给业务 OSDK 或 Ontology MCP，让业务自己开发 Application，谁来开发都可以。但问题是，我们必须明确在同一个系统里保留哪些管理连接和关键变量。

如果把人机交互层完全交给外部，这一层的数据就不会天然沉淀进 EOS。这也是为什么我们短期放弃了 AIP：我们暂时不自己做完整 Agent，也不管理 Agent 全部执行过程中的审计、Traceability、Tracing 和 Session 跟踪，先交给外部工具。结果就是这套交互数据不会天然进入 EOS。但为什么现在放弃？因为我们下面的基础能力还没有做好，外部产品又在高速变化。

AIP 暂时做不过外部产品。我们可能有管理优势，但没有应用体验上的优势。我研究了一个月，最后选择暂时放弃。但 AIP Logic 有没有意义？绝对有。AIP 与 AIP Logic 是两个概念，不在同一个管理体系里。现在我们选择的是一个最小范围，但以后仍然可能重新打开，因为我们最终必须有一种原生的人机对齐方式，告诉大家：按照这套方式做，整体一致性最好。否则，大家做出来的前端质量会参差不齐，而且无法和全栈能力真正连起来。

我们做 Workshop 和 Notepad，就是想观察人机交互的最佳实践。是不是一百多个组件就可以覆盖大部分人机对齐逻辑？这个问题非常需要回答。回答出来以后，上下贯穿的人机交互才会通。所以我们一定会做 Workshop，后面也可能做 Notepad。人机交互大体有两类体验：一类是表单式，一类是文档式。现在文档也在应用化，块文档已经越来越像 Application，但文档仍然是文档，因为它是流式布局，可以无限延伸。这两类体验未来怎样与 AI 结合，还需要继续观察。

（中场休息时，现场有人补充：）所以一开始说 EOS 干什么，EOS 首先是本体，下面的治理框架也非常关键。P 部门现在做的 Global Branching、Compass、权限、审计、DevOps、血缘等能力，都是这一套治理底座的一部分。这些能力并不时髦，但非常专业，也是 EOS 真正的基础。

回到我们的工作。在我的控制圈里，我会全力以赴。一个控制圈，就是企业数字平台自身的数字化过程。今天我刚和永新开完会，我们会启动一个项目，安排四五个人全职去做企业数字平台未来整个流程体系的规划和设计。当然，还是要从调研和学习开始。

我们做事情，先从穷举开始。一汽和我们交流数字化时，说得特别朴实：做事就三个步骤——数数、分类、定标准。一万个以内的变量都应该先数出来；第二步分类，重新抽取它们的共性；第三步制定新的标准。做技术和非技术业务都一样。

我们在数字化过程中有自己的方法，但真正实操时仍然需要穷举。第一是方法论的穷举：IT、CICM、PCF、APQC 等体系分别覆盖了什么，哪些指标体系和流程体系可以借鉴。第二是业务的穷举：今天到底有哪些业务、有哪些盘点、有哪些困难和困扰，这些问题能否映射到我们的方法中。

但我们有自己的“消化肠胃”。理想最终会形成一套自己的企业架构方法。外面的东西都可以塞进来，经过这套肠胃消化，最终成为我们自己的方法。

做这些事情也需要平台支持。未来所有流程规划、流程建设和中间场景，都必须落到系统里。不落系统就一定会挥发、一定会腐化。要落系统，就落到 EOS，不再建设一套套分立系统。初期可以用 GitLab 整理材料、做小原型，都可以，但最终一定要进入系统。这就是未来三年的规划，也是 EOS 这项关键投资的意义：做 One System，由一个系统承接所有。

这不是今天突然想到的。2024 年底，我们就意识到应该重新做一个系统。这个系统要有统一的权限体系、统一的工作台，以及统一的低代码建模能力。那时主要参考 ServiceNow 等产品。大家可能不知道，ServiceNow 两三百个教学视频我都组织翻译过。我自己买课程、买书、看视频和线上教材，不断校准中间的逻辑。今天告诉大家的，是长期脑力劳动的结果，不是开门拍脑袋，也不是看几篇公众号文章得出的。

有人问节奏。其实所有事情都有节奏，这在去年底的 BP 里已经写了。最早想做统一平台，是 2024 年底。整个计划分为基础阶段、爬行阶段、行走阶段和奔跑阶段。真正的大规模转变要到 2028、2029 年，到了关键节点，所有东西才会开始加速转换。养兵千日，用兵一时，变革点发生在那个时间。每一块都有自己的逻辑和时间节点，我不会把自己没想明白、没有边界的无限期目标直接拍给大家。所以不要着急，也不要慌。

问：长远来看，EOS 两到三年的终局里，哪些能力必须成为核心壁垒？

其实刚才已经说了。Foundry 最值钱的，是 Multi-resource Global Branching，以及 Privilege、Marking、Lineage、Auditing，也就是权限、标记、血缘和审计体系。这几个理念贯穿产品的所有细节。因为有这些理念，每个 Resource 都必须有显性的 RID，权限怎样穿透也必须能够计算。

这个产品难在哪里？在 Palantir 以前，这些概念从来没有同时出现在一个系统里，更没有用同一套机制覆盖所有 Application。今天很多组织已经发现了这个问题，都想从自己的立场出发，重造、重塑或者扩大自己的产品范围。

尤其在 Agent 出现以后，不要以为原来的软件公司不聪明。Salesforce、SAP、Snowflake、Databricks、Microsoft 都非常清楚自己的产品在 Agent 时代面临什么问题，都在拼命扩边、破圈。但有两样东西很难突破：一是市场对它的定位，二是它内部既有的组织架构。

举个例子，Snowflake 有没有可能成为 Palantir？很难。它做不了完整的 Application 闭环。因为它很难站在企业面前说：“我不只是做数据库、做数据湖，也不只是让既有数字资产可以被访问；我要帮助你做流程再造。”Snowflake 很难站在 CEO、CIO 面前说这句话。从公司的基因、市场定位到产品结构，每一个环节都在限制它。它可以让既有数字资产被理解和访问，但没有完整的写回和业务闭环，所以事情只完成了一半。

微软有没有可能？微软是全栈的，有 Dynamics、Fabric、Agent 平台，什么都有。它有资格站在 CEO 面前说这句话，但能不能做成？仍然很难。因为它必须打破内部组织墙。原来各个平台都是独立产品线，宏观架构看起来彼此连接，真正实操时却很难连起来。做云服务的同学都理解：你会发现这些云产品缺少统一的系统设计，多的是内部赛跑和竞争。

微软内部有 MAS、GitHub、API、Token、Agent 平台以及其他产品。如果这些产品彼此只是 Partner，而不是一个系统，就无法统一站在企业 CIO 面前说：“我来帮你完成一次流程改造。”因为每一条产品线都要卖自己的产品，系统之间不挨着，权限不通、数据不连，整体仍然是松散的。

这就像创业公司拼装自己的系统：从 Auth0 买身份和授权，从另一个 SaaS 买 CRM，再买财务系统、日志系统和 Datadog，最后凑在一起。让 Agent 穿透这一整套系统，没有那么简单，因为后面总有一部分看不见，也很难用一套元数据统一。做大数据这么多年，大家都知道元数据系统有多难。你在上面再叠一层，下面各产品天生又不是同一种设计口味，相当于要把不同维度、不同逻辑的系统强行整合到一起。

所以很多组织不是不知道事情应该怎样，而是受既有结构限制，很难完成深刻变革。大家一定要分清：事情应该是什么，和现状是什么，中间存在巨大偏差。事实不等于应然。今天看到的现状，只是既有利益相关者和既有利益形成的一个快照，不等于未来，更不等于变革。

举个例子。2007 年苹果出来以前，大家认为智能手机应该是什么样？拿一支笔去点，最好还有键盘，运行 Windows Mobile。微软沿着原来的道路不断做，系统越来越慢，大量精力耗在复杂的技术机制上，开机甚至要很久。苹果出来以后，整个逻辑被重新定义：高度整合一致的系统、极其流畅的用户界面，拿掉触控笔和键盘，重新定义操作系统，也重新定义用户需求。

这个世界一直是在企业家重新发现需求的过程中变化的，绝不能把现状当成未来。我们现在看到了 AI Agent 的强大威力，也越来越清楚阻碍它的东西主要是什么。第一，人和 Agent 对齐的速度；第二，你敢给 Agent 多大的运行空间。这里“敢”字很重要，因为它意味着安全、审计和沙箱化，而不是把生产力的魔鬼直接放出来。

我们个人给 Agent 创造的环境够不够？组织给 Agent 创造的环境够不够？都不够。这就是机会点，也是真正的需求，是最硬的需求、最大的杠杆。

问：为什么 AIP 没有着急做？

这是有选择的。现阶段不应过早把 AIP 纳入强管理体系，因为在这一块，易用性、可用性暂时比可管理性更重要。用户还在不断追求个性化生产力释放。我们去一线门店，发现不少店长、店员还在自费订阅外部 AI 工具。这说明用户首先希望工具更好用，不应该过早把它完全纳入 Management 体系。当然，另一个原因是我们的基础能力还没有做好。

问：未来产品定位是否继续以 Foundry 为主？

很多人会怀疑 Foundry 是否代表未来，因为 Foundry 的界面看起来比较古早，单体产品也不时髦。界面当然会变，但什么时候变、怎样变，一定要由一线业务驱动。Foundry 今天沉淀出的交互体系和逻辑，也来自它的客户。我们今天先把其中已经被验证的东西消化进去，未来真正生长时，养料一定来自我们的客户和业务实践，而不是坐在这里凭空编出来。

在业务推进过程中，从部门内部走到部门外部，各种创意和创造力才是未来产品生长的养料。但别人凭什么使用你的产品？你首先得有一个可用的基础，让他用起来。这里既包括我们内部控制圈里的增长，也包括外部影响圈带来的增长。交付形式会变，但水面下那套高度抽象的概念体系很难变。

AIP 在整个 Foundry 体系里，只是一类 Application。它现在很时髦，但如果这一波热度稍微过去，它和 Workshop 这样的 Application 并没有本质区别：它们都在创造资源。AIP 创造的是 Agentic 执行路径、对话路径，这些资源未来也可以用于流程挖掘和数据挖掘。

Foundry 的工具大体无非两类：一类创造资源，一类发现资源。Workshop 用来创造 Application，Notepad 用来创造应用化文档，Vertex 用来发现新的关系和理念，反过来指导今天的资源是否需要创建、读取或修改。流程工具也是在做类似的事情，根据状态进行推演。

所以再强调一遍：One System 对公司的变革极其重要。变革会加速，所有事情都在一个系统里做，才有可能形成共同的方法和共识。如果分散在不同系统里，人会被共识成本击溃。在我们这样复杂的组织里，再大的管理能量也会被分立系统吃掉。

华为当年是在极其特殊的历史机会中，靠几千人的核心队伍、几万人长期肩拉手扛，又赶上公司上升期，花了三十年才完成这样的组织变革。这样的历史机会，不只是我们可能没有，全球很多企业都没有。华为早期的人才条件并不像今天想象得那么好。那个年代，最优秀的人往往出国、去外企或国企，去华为的很多人来自农村，条件非常艰苦，上学甚至要自己背米。华为靠时代红利，也靠任正非对人性的理解和对自己的高要求，把一批普通人长期组织起来，才走到今天。

问：EOS 未来的使用场景还不清晰，能不能展开讲一下？

我的目标很明确：未来所有业务平台、所有决策支持系统，都可以在这里。先从我们自己做起，从企业数字平台内部开始，一点点推广、不断生长，进入迭代飞轮。最终会不会连现在的 CRM 也有人提出迁进来？有可能。走到那一步，自然会有很多人说：“干脆把这个也做到 EOS 里吧。”不用我们主动要求。

今年不要谈太多生产级用户量。今年的主要任务，是把基础能力交付出来，先在企业数字平台内部开始使用。现在离目标还很远，9·30 还有很多工作，Marketplace 等自举关键能力还没有完全就绪，Workshop 的版本和一些 MVP 能力也需要继续补充。所以今年主要还是内部建设，和长期计划一致，不要慌。

问：感觉规划里缺少 AI 这一环。AI-native 应该怎样理解？

先不要往自己脸上贴金。即使今天用了 AI，也不等于你的工作就是 AI-native。什么叫真正的 AI-native？没有 AI，就没有你这份工作。比如做大模型、自动驾驶、具身智能，没有 Transformer，这类工作本身就不存在，这才是真正的 AI-native。

我们大部分人并不是 AI-native，只是在把 AI 当作生产工具使用。那就不用急着给自己贴标签，先找到自己的业务是什么，怎样养活自己。EOS 也一样，它更准确的说法是 AI-enabled：让 AI 穿透整个系统，帮助个人和组织提升效率、发现问题、解决问题、改变流程，不断迭代。最终目标，是不管组织多大，都有一套价值增值网络：管理能量和资金投入进去，绩效和业务价值产出出来。

即使没有 AI，组织也不是绝对不能做这件事。靠信息化可以，甚至靠卡片、纸片也可以。传统制造业过去就靠纸质卡片、流程标准和制度建立结构化工作方式。福特流水线、丰田精益生产，都发生在今天的 AI 和计算机之前。有了 AI 和计算机，只是能把这件事干得更快、更好。所以没必要争抢 AI-native 的标签，AI 工具最终会变成一种普遍能力。

两年后的毕业生，必然天然会使用这些工具。我昨天在拟下一代校招生标准，连名字都改了，叫“IT 全栈管培生”，不再叫软件工程师。进来以后跟着业务走、跟着业务打，在业务增值过程中培养数据、开发和产品能力，最后根据特点站到不同角色上。

2022 年我第一次做校招时，ChatGPT 还没出来。那时即使招了很多算法背景的人，不少学生也没有大模型实践。到 2024 年再校招，不管什么专业，甚至机械专业的学生，也可能做过模型预训练，有过 AI 实践。再过两年，毕业生会自带这套思维方式和工作方式。

所以会不会使用 AI 工具，就像会不会使用未来的 Office。今天大家觉得 Office 很简单，但把它给上一代人，不一定学得会。我在我妈四十岁时就尝试教她用 Office，也没教会，双击这一关就可能卡住。你觉得与生俱来、很容易的东西，其实来自所处时代。今天你觉得困难的事情，对未来的小孩来说可能成本极低。

但工具不会自动消除能力差异。复杂工程中的很多规范和共识，都是经历多年实践、长期沟通以后才形成的。在复杂组织里，个别聪明人改变不了整个环境。一个十倍员工混在一堆一倍员工里，靠个人很难推动整个组织改变，最后往往会被拖垮。真正的变化仍然要靠组织从上往下推动。

组织从上向下给出要求和引导，个人先提高认知、改变自己，再横向拉通、拉齐。AI 到来以后，组织协同的基本逻辑没有变，但要求更高、紧迫感更强。以前一个变化可以花一两年，AI 来以后可能压缩到三个月、六个月。比如供应链里的 AI 工程端到端，以前两周一个 Sprint，现在可以一周一个 Sprint，甚至三天一个迭代。

AI 确实在提升效率，但它首先是在现有流程基础上把事情做得更好。比如投入 30% 多的预算，完成全年 50% 的 IT 项目，交付团队和业务都很高兴。李源他们交付明显变快，团队自己知道，业务也知道。这些都是把原来的流程做得更好。

问：EOS 的资源投入够不够？现在团队人多了还是少了？

从工作量看，有太多东西还没有做完，当然会觉得人少。但平台研发人数未来未必会越来越多。在这个时代，人多不一定是好事。这个产品最难的地方，不是有多少任务可以分，而是概念一致性。Foundry 最难的就是概念，需要长期认知和理解。做惯短平快项目、习惯短期计效的人，在这里不会舒服，因为要费脑子、理解很多东西、想很远，才可能为自己找到一条价值路径。它是反短期计效的。

人多会带来认知破碎，也就是我说的“人多心必碎”：有的人多看一点，有的人少看一点，还有人始终在讨论别的事情，但平台又要求概念高度一致。Palantir 用很多年才做到这一点。这家公司一直反潮流、反主流技术认知，不追逐技术热点，只盯客户真正的风险，所以它才能走到今天。

我讲 FDE 时说过，FDE 必须同时承担两个职责。第一，到客户现场识别流程、再造流程，把最有价值的问题真正解决。仅仅帮客户做一个项目，不叫 FDE。第二，必须具备平台杠杆意识。客户现场形成的所有可部署资产，都要沉淀进平台，下一次再做流程识别和流程再造时可以复用，形成循环。

同时，FDE 还要把客户现场形成的可部署成果带回平台，告诉平台下一步应该补什么。平台再调校和收敛概念，形成未来的产品。所以 FDE 本质上由平台投资，它可以不直接向客户收费，长期依靠平台价值回收。我们现在是在反向咀嚼、理解 Palantir 多年积累的成果，这是一项很难的反向工程。

这种事情不能一开始堆很多人。人越多，责任越容易分散：十个人会觉得自己只占十分之一，五个人觉得自己只占五分之一，三个人才更可能产生“除我无他”的责任感。复杂的事情必须有人带头、全力以赴。如果真正关心的人还要耗费大量精力说服那些觉得与自己无关的人，成本会非常高，而且短期看不到绩效。

在座有几个人经历过二十年的技术周期？大部分人只经历过上升期，然后突然掉下来，甚至没有完整经历过一个短周期。做未来的事情，从工作量看当然需要更多人，但从组织战斗力和认知一致性看，可能就需要这么多人，甚至可以更少。认这件事，就全力去打；如果不认，也可以选择离开。概念复杂，要学、要看的东西很多，必须高度自驱、自律。

我们是在用今天的时间换未来效率，用今天的低速换未来的高速，用概念的一致性和完整性换未来的效率，不是在追求今天的账面效率。今天宁愿让大家停下来拉齐，也不能把任务一分，张三、李四、王五各自走掉，最后再也拉不回来。

Palantir 没有把这套体系完整写出来，因为它是在漫长过程中由上千人迭代出来的，可以先靠资源堆，再逐步收敛。我们不能走这条路，也不应该走。今天有 AI，一旦自己的 Pipeline 和逻辑走通，就应该尽量让 Agent 来做。我们不是靠堆人解决问题，而是重构 Pipeline、重构认知，把知识沉淀下来。

所以 EOS 核心团队的资源会保持克制，不会无限增加。具体业务领域可以有人进入，在 EOS 上开发自己的 Application，这不算核心平台团队的扩张。架构团队真正思考的，是怎样用认知杠杆、流程杠杆和系统杠杆撬动效率。过多人员会带来巨大的沟通成本和认知成本。

难点在于，这些事情不是显学。写一个 Harness、做一个 Ontology Demo，或者用某个 Python Agent 框架做周末项目，都是显学，所有人都能玩。最后很可能是你写的别人不用，别人写的你也不用，互相还瞧不起。但这些都没有壁垒。真正有壁垒的，是不那么时髦、却能长期形成组织能力的系统和方法。

（主持人）下面回应问卷里大家认为最应该改变或优化的事情。包括新的开发范式下质量不够健壮、模块需要解耦等问题。

我们一直说自驱，但其实离真正的自驱还很远。从 0 到 1 的冷启动阶段，主要挑战是底层逻辑对齐。这件事我和 P 哥 PK 过很多次，有一次甚至争到 P 哥脸色都变了；我也和兰兰、小龙、沈艳等同学反复讨论。我们原计划在 6·30 发生一次跃迁：依赖 DevOps、Marketplace 等产品，让我们开发 Compass、Account Settings 或任何平台能力时，和开发一个订单系统没有本质区别。只有极少数底层能力需要在 Service 里供给，整体开发模式应该一致。

现在就卡在这里。DevOps、Marketplace 以及评测等能力还没有完全就绪，所以冷启动阶段还没有过去。

问：在这种情况下，采用什么协作方式更好？

我觉得自运营更好。否则大家又会变成单纯的执行者，和纺织厂女工没有区别：不需要做任何决策，别人告诉你怎么干就怎么干。现在单纯写代码已经可以交给 AI Coding 和各种工具，人的价值还是要离业务增值更近，自己做出决策。

还有一点，做平台要尽可能一步到位。范围可以不全面，但深度不能不够。发现深度不够，我一定会提出要求。每个人都要站在一个 Scope 负责人的角度，据理力争，而不是只做咨询。简单执行工作可以交给 Agent。

我看过很多部门做的 Agent 产品，十万行、二十万行代码，看起来很复杂，但不要把代码量本身当成优势或能力。里面 80% 的能力来自优秀模型。真正属于团队的能力，是业务认知，是知道这件事为什么要做成这样。

未来大家也一样。我们做 EOS，承载的是对未来组织中最难治理问题的理解和愿望：怎样让一个组织在有模型的基础上不断提高治理效率？因此，EOS 不是堆砌越来越多的 Application。每增加一个 Application 都要非常小心，尤其是核心 Application。

Foundry 里既有做得非常好的东西，也有有缺陷的东西。随着研究深入，我们看到的缺陷也越来越多。比如 Notepad 如果能与飞书一部分能力结合，可能会更好；Foundry 也有不少 Application 逐渐处于半废弃状态，有些能力在 Gotham 中存在，在 Foundry 中已经消失。它同样经历了长期沉淀和变化，不是每一样东西都值得照搬。

AI Coding 会给人一种“无所不能”的幻觉，但真正的边界仍然是你的认知边界，以及你怎样抽象问题。刚开始使用 AI Coding 时，人最喜欢做的是把自己熟悉的东西再做一遍，或者看到别人的东西不错，就让 AI 再做一遍。这样没有产生新的认知，也没有形成真正的能力。

我们要做的，是把三万人组织的数字化建设底座做出来，不光包括 EOS，也包括相应的方法。我们部门不缺活，但要看是什么活。原来那种活可能会消失，因为业务可以自己完成。

过去我们的软件产能严重不足。峰值时有七百名正式员工、二百五十名岗位外援，还有一两百名项目外援，整个体系有上千人在做 IT 系统。现在一方面业务预算在收缩，另一方面很多工作业务自己就能做。原来必须靠软件人员完成的工作，至少减少了 30% 的产能需求。

为什么正式员工感受不明显？因为最先减少的是项目外援和岗位外援：二百五十名岗位外援已经减少到不足五十人，正式员工只减少五六十人。正如那句话，“死人不会说话”，没有声音不代表事情没有发生。

另一方面，留下来的事情反而更难。工作变了。如果还只会做原来的事情，业务自己就能做，人的业务价值会下降。业务真正会找我们做什么？是它自己做不了的更深层问题，比如业务建模和真正复杂的 Application。很多东西业务可以做出 Demo，却无法工程化、无法上线，可以说“生于 Dev，死于 Test”，最后还会回来找我们。

这类工作更难，因为很多人的知识储备不足。过去是产品经理画 PRD，研发负责实现，做不过来就找外援，再给外援一套脚手架，往里填人肉 CRUD。现在简单工作不再需要这么多人，留下来的工作却越来越实、越来越深。

本体分析、本体治理又是另一套知识体系，还包括 RDM 等方法。为什么不能直接照搬某个平台的本体表达？因为有些表达语义描述性不强。为什么平台没有选择语义最强的道路，而采用更偏功能化的表达？因为它首先要形成工程共识、完成工程交付，不能给业务增加额外成本。很多工具体系、建设体系和治理能力都在后面。未来的活会越来越深，认知要求越来越高，难度越来越大，知识面越来越宽，只是不再是原来的那种工作。

问：除了参考 Palantir，还有没有其他对象可以参考？比如国内友商蔚来、小鹏，他们是怎么解决的？

没有完全可照搬的对象。我比较了解不同车企的 IT 逻辑。比亚迪的 IT 是分散的。它有很多国内、海外业务和车型，IT 力量大多沉在下面。中央也有 IT，但更多负责汇总和集团公共任务，大概一千多人。大部分大型组织的 IT 都不是一个 IT，而是无数个 IT。

美的也是这样。集团层面最容易看到的是一个 CDO 部门，主要做数据汇聚，真正的 IT 能力沉在各业务单元里，因为业务就是这样发展起来的。很多传统车企也一样：售后有售后的 IT，零部件有零部件的 IT，集团有集团的 IT，零售又有自己的 IT。它们是分散的，所以很难用一个统一的大思路解决问题。

我们公司的 IT 比较特殊。经过这些年整合，我开玩笑说，我们可能是全球车企里 Scope 最大的 IT 之一。大部分企业很难把这么多领域放在一套组织和方法下思考。

蔚来、小鹏也有各自的发展路径。有些新势力的 IT 还没有完成一个转换：从“IT 是技术部门”转换成“IT 是业务增值和业务变革的一部分”。有些 IT 负责人来自安全、技术或学术背景，不是业务出身。只靠技术背景，很难把这个问题想完整。

很多成熟企业的 CIO 都做过多年的业务主管。比如红旗的一位负责人，做过海拉灯具厂厂长，也做过大众供应链以及其他业务岗位。只有经过多个业务岗位历练，才更可能做好 CIO。很多新势力的 IT 主管主要是技术出身，还没有足够时间完成这种沉淀。

结果就是，他们容易把商业应用、领域应用和底层平台分开，各自建设，接不起来。我们希望走的是另一条路：平台和方法学必须同时对上，用方法帮助业务梳理企业架构，再用平台承载这些架构。两者接起来，才可能把从上到下的链路真正接好。

不同公司的发展历程，最终会导致完全不同的结果。王岱提到的这个 Idea，也是从原来的车联网业务里一步步生长出来的。
